See [labelstud.io/tags/](https://labelstud.io/tags/) and [labelstud.io/guide/setup.html](https://labelstud.io/guide/setup.html) for the documented substitution mechanism this relies on.

## Confirmation that every Sol prediction corresponds to the exact V1 output displayed

Each task's `predictions[0].result` is built exclusively from that same V1 record's `judge_assessment.annotations` — the identical object read to populate `data.output_text` — so there is no possibility of a task's displayed output and its imported prediction coming from different records or versions. For the 13 span-anchored annotations, this was additionally verified mechanically: each annotation's `span` string was located inside that exact `output.text` via `str.index()`, which raises an error if the substring is absent — so a `start`/`end` offset could only be computed at all if the span text is genuinely present in the displayed V1 output. All 13 resolved successfully with **exactly one** occurrence each (checked via `str.count()`), so no offset is ambiguous between two possible matches.

`predictions[0].model_version` is set to `judge_assessment.judge_model_name` (`"GPT-5.6 Sol"`) for every task, associating the prediction with both the correct task (by being embedded in that task's own object) and the correct model (by name, taken directly from the source record).

## Schema mappings and unavoidable limitations

- **Dimension/subtype → `Labels`/`Choices` values:** every one of the rubric's 24 `dimension: subtype` combinations (7 dimensions from `data/rubric.json`) is enumerated verbatim in `label_config.xml`, as `"<dimension_id>: <subtype_id>"` strings — not renamed, reworded, or filtered to only the combinations that happen to appear in the current data. This was a deliberate choice: it means the config is a complete, faithful translation of the rubric (a reviewer can tag anything the rubric defines), at the cost that most of the 24 values will never be exercised by an imported Sol prediction in this sample (see below).
- **Severity → `Choices`:** the rubric's exact three severities (`minor`, `major`, `critical`) are used verbatim, with no added or renamed values.
- **`span: null` annotations → a second, non-region control set:** Label Studio's region-based `Labels` control requires a real `start`/`end` character offset; a `Labels` result cannot exist without one. Since 1 of the 14 Sol annotations (T09's `constraint_compliance`/`length_violation`) has no specific span, it is represented through an independent, non-`perRegion` `Choices`/`TextArea` control block instead (`doc_dimension_subtype`, `doc_severity`, `doc_rationale`, `doc_suggested_correction`) rather than forced into a fabricated or synthetic span. This mixed region + document-level result pattern within one prediction's `result` array follows Label Studio's own documented example (their bounding-box template combines region `rectanglelabels` results with a plain `choices` result in one prediction) — see [labelstud.io/guide/predictions](https://labelstud.io/guide/predictions).
  - **Known limitation:** this document-level control block can only represent one whole-output issue's dimension/severity/rationale/correction as a coherent set at a time. The current data never needs more than one (T09 is the only task with any null-span annotation, and it has exactly one), so this wasn't exercised further, but if a future task's Sol assessment had two or more null-span annotations, this flat structure could not keep each dimension/severity/rationale/correction combination correctly grouped without ambiguity. No such case exists in the current 10 V1 records, so this is a documented latent limitation, not an active defect.
- **`suggested_correction: null` → omitted result item, not an empty string:** 1 of the 14 annotations (T07's) has `suggested_correction: null` in the source. Rather than emit a `textarea` result with empty text (which would misrepresent "Sol gave no correction" as "Sol gave an empty correction"), no `span_suggested_correction` result item is emitted for that annotation at all. All other 13 annotations have a non-null `suggested_correction` and do get that result item. (All 14 annotations have a non-null `rationale`, so this situation never arises for that field in the current data.)
- **Rubric dimensions never exercised by any Sol annotation:** `terminology`, `style`, and `audience_appropriateness` have zero annotations anywhere across all 10 V1 records (confirmed by iterating every `judge_assessment.annotations` entry in `data/v1-results.json`). The labeling config still defines controls for these, but no imported prediction in either output file will ever populate them. This is a property of the source data, not a mapping gap.
- **XML/JSON escaping:** all `Label`/`Choice` values and task data strings were passed through standard XML/JSON escaping during generation (`&`, `<`, `>`, `"` handled for XML attributes; native `json.dump` handling for JSON). Both output files were parsed back (`xml.dom.minidom.parse`, `json.load`) after generation to confirm well-formedness, not just visually inspected.
