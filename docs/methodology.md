# Methodology

## Why locale-conditioned generation, not translation

The goal of this project is to practise evaluating a common real generative-AI task: producing same-language marketing copy conditioned on a target locale (spelling, date/currency conventions, terminology, brand voice). This is a different problem from translation quality, which is what the MQM framework was originally built to assess. This project borrows MQM's *concepts* (selecting a bounded error taxonomy, assigning severities, deriving a status from points) without claiming to be a translation-quality evaluation. Results here are described as **MQM-informed**, never "MQM-compliant."

## Why `en-AU`

Australian English has well-documented, checkable divergences from the more common training-data defaults: British-derived spelling (colour, customise, moisturiser), day-before-month dates, and everyday terminology differences (doona, takeaway, trolley, chemist). A reviewer with no specialist localisation background can verify most findings here directly against the stored context and output, which keeps the whole case study inspectable, rather than requiring the reader to trust an opaque judgement.

## Why synthetic data

Every task, business name, brief and user prompt in `data/tasks.json` is invented for this project. No real user, customer, or production data is used anywhere. This keeps the repository safe to share and inspect, and avoids any implication that this reproduces a real organisation's data or workflow.

## The rubric

Seven dimensions, each with two to eight subtypes. See `data/rubric.json` for the exact, current definitions (this file should never restate them in a way that could drift out of sync; read the data file directly).

Six of the seven dimensions are adopted directly from the **MQM Council's MQM Core error typology** (verified live at <https://www.themqm.org/mqm-pillars/the-mqm-core-typology/> rather than recalled from memory; an earlier draft of this rubric got several names wrong by relying on memory, which is exactly the failure mode this note exists to avoid repeating): Terminology, Accuracy, Linguistic conventions (named "Fluency" in MQM v1), Style, Locale conventions, and Audience appropriateness (named "Verity" in MQM v1). MQM Core's seventh dimension, Design and markup, is omitted entirely: the generated output is always a single plain-text paragraph, so a dimension about headings, layout and markup has nothing to apply to here.

Within each adopted dimension, only the subtypes plausible for locale-conditioned marketing-copy generation are kept. Most notably, Accuracy's MQM subtypes `Mistranslation`/`Overtranslation`/`Undertranslation`/`Untranslated`/`Do not translate` are dropped rather than renamed, because they are all source-text/target-text bitext concepts with no equivalent in monolingual generation against a brief. Every dimension and subtype in `data/rubric.json` carries a `source` field (`"mqm_core"` or `"project_addition"`) so this mapping is inspectable in the data itself, not just asserted in prose.

The seventh dimension, **Instruction & constraint compliance**, has no MQM equivalent and is this project's own addition: MQM assumes a translation task with no concept of an arbitrary user-supplied constraint like a word-count ceiling, because a source text doesn't have one; this project's ten tasks do.

Severities carry fixed point values (minor=1, major=5, critical=10) chosen to make critical errors dominate a status regardless of how many minor issues are also present, while still letting several minor issues accumulate into "Needs revision." Status classification does not actually depend on critical's exact magnitude (`status_policy.critical_forces_fail` makes any critical annotation an automatic Fail regardless of point total), but the magnitude does matter for severity-weighted aggregates (e.g. "error points by dimension" charts), where a single critical annotation can visually dominate a chart out of proportion to how many records it actually affects. The original brief (drafted with ChatGPT's help before this build) specified minor=1/major=5/critical=25, a ×5 step at each tier; that was revised down to critical=10 (a ×2 step from major) specifically to reduce that skew risk, since 25 had no other justification behind it. These point values and the status bands below are project-specific choices, not taken from MQM's own scoring model. Status bands (0–1 Pass, 2–4 Needs revision, 5+ or any critical Fail) are a simple, disclosed policy choice for this MVP, not a validated production threshold; see `data/rubric.json`'s `status_policy` for the authoritative version.

**All seven dimensions are weighted equally.** A minor-severity annotation costs the same 1 point whether it's tagged `linguistic_conventions`, `accuracy`, or `style`: only severity determines points; which dimension it's filed under does not. `data/rubric.json` has no per-dimension weight or multiplier field. This is a deliberate simplification, not an oversight: a more mature rubric might reasonably weight some dimensions more heavily than others at the same severity (e.g. treating a minor factual slip as worse than a minor style slip), but this MVP keeps scoring uniform across dimensions to keep the points-to-status arithmetic easy to audit by hand. Dimension-level weighting is a reasonable extension this project doesn't attempt.

## Human evaluator assessment vs provisional LLM-as-a-judge

Both assessments see the same task, target-locale information, output, and rubric. Neither is exposed to the other during its own creation:

- The **human evaluator assessment** is the primary curated record for this MVP. It was drafted with assistant help and then explicitly reviewed and approved by Giles before being committed; see [provenance.md](provenance.md) for exactly what was reviewed and when. It is labelled *"Human evaluator assessment: created by the MVP author for demonstration"* throughout, and is never called expert judgement, gold-standard data, or validated ground truth.
- The **provisional LLM-as-a-judge assessment** comes from a separate model (GPT-5.6 Sol), run independently by Giles outside the build session, using the exact prompt in [judge-prompt.md](judge-prompt.md). It never sees the human evaluator's assessment, and (because its prompt omits the V2-only locale profile and glossary context and is otherwise identical in shape for V1 and V2) it is not told which generation version it is judging. It is a comparison signal, not a source of truth; ten examples do not validate or calibrate it (see Zheng et al. in the README references for documented LLM-as-a-judge biases).

## Lightweight retrieval-augmented context (V2)

V2 augments the same `user_prompt` with two deterministically retrieved inputs: the `en-AU` locale profile, and any glossary rows from `data/terminology.csv` whose scope matches the task's content category or task ID (see [data-schema.md](data-schema.md) for the exact retrieval rule). This is plain keyword/alias matching over a CSV file: no embeddings, vector database, semantic search, or external retrieval service. It is described honestly as **lightweight retrieval-augmented context**: it demonstrates retrieval, context construction and grounded generation, not sophisticated semantic RAG.

Task-specific fixes are never written directly into the V2 system instruction. Any correction a task's output needs must come from a glossary row that would also apply to other tasks sharing its category, or from a row explicitly scoped to that task as brand guidance; never as an ad hoc patch invented after seeing the V1 error.

## From V1 observation to recommendation

Three findings are recorded in `data/findings.json` and rendered, with evidence links back to the full V1 records, in View 4 of the app. All three follow the same reasoning chain: observation, examples, alternative explanations considered, hypothesis, and a proposed recommendation.

**Ordering.** All three findings drive a recommendation; they differ in *type* (`recommendation_type` in `data/findings.json`: `"system_change"` or `"evaluator_training"`), and are ordered by that field: both `"system_change"` findings first, then `"evaluator_training"`. Finding 1 and Finding 2's recommendations are both now built into V2, bundled into the same revision rather than tested as separate versions (see [limitations.md](limitations.md) for the trade-off that involves); Finding 3's `"evaluator_training"` recommendation isn't implemented anywhere in this build. This isn't ordered by severity, error-point total, or affected-task count: Finding 2 below affects more tasks (6/10) than Finding 1 (5/10), but Finding 1 comes first as the finding that originally shaped V2's design.

**Finding 1 (recommendation: system change, built).** 5 of the 10 V1 outputs (T02, T06, T08, T09, T10) default to a non-AU-locale convention where the en-AU version differs, despite the V1 system instruction naming the target locale by name: a US spelling variant ('favorite', 'traveler', 'moisturizer', 'Enroll'), a US-ordered date (T10's 'March 20' rather than '20 March'), or an everyday AU term replaced with its US/generic equivalent (T08's 'coffee to go' rather than 'takeaway coffee'). Four of the five tasks are corroborated by both the human evaluator assessment and the independently-run LLM-as-a-judge assessment with identical spans; the human evaluator's assessment was drafted before the judge was run, so this is two independently-produced assessments agreeing, not the judge creating the pattern. T08's terminology miss was caught only by the human evaluator, a genuinely weaker single-sourced piece of evidence disclosed as such rather than folded in as if equally strong. The five tasks span five different content categories, ruling out a single-domain artefact, and every flagged pair is an unambiguous, well-documented AU/US convention, ruling out a rubric-ambiguity explanation. The hypothesis: naming a locale is not the same as supplying its conventions, and V1 supplies none, for spelling, date order or terminology alike. This is a context-supply gap, not a generation-capability limit, so it motivates a specific, testable recommendation: deploy and test a generation system configuration that retrieves the en-AU locale profile (`data/locale-profiles.json`) and matched terminology glossary rows (`data/terminology.csv`) into the context packet alongside the system instruction. The honest caveat, disclosed in the finding itself, is denominator fragility: 5/10 is a real concentration but a small one.

**Finding 2 (recommendation: system change, built).** 6 of the 10 V1 outputs (T01, T03, T06, T07, T08, T09) add a claim, offer, or mechanic the customer's own prompt never gave. This was originally surfaced only by the LLM-as-a-judge (7 of 10, before T05 was reviewed and excluded as closer to ordinary category-typical language than a clear violation); rereading each of the remaining 6 spans against its own source `user_prompt`, rather than taking the judge's word for it, confirms each is a genuine, checkable addition: T01's 'our best-selling outerwear' and 'made to keep you warm' both violate an explicit "don't add fabric or unverified claims" instruction; T09's added skincare claims go beyond an explicit "use that exact wording, nothing stronger" instruction; T03's invented free-class offer substitutes a different commitment for the "7-day free trial, say exactly 7 days" the customer explicitly asked for; T06's "off your first purchase" narrows an offer the customer authorised without that restriction; T07 invents a launch timeframe never given; T08 invents an app-interaction mechanic never given. The six tasks span six different content categories, ruling out a single-domain artefact. The hypothesis: V1's system instruction says to preserve supplied facts and satisfy stated constraints, but never tells the model to avoid adding anything beyond what's supplied, so it tends to embellish with plausible-sounding but unauthorised claims. This motivated a specific, testable recommendation: add an explicit no-fabrication constraint to the system instruction. That constraint is now built into V2, bundled into the same revision as Finding 1's locale-profile fix rather than tested as a separate version (see [limitations.md](limitations.md) for that trade-off). One disclosed side effect: removing the unsupported content from T06, T08 and T09 dropped those three below their required word count, since the fabricated content had been padding them out; that shortfall is recorded in each record's `output.generation_notes` rather than papered over.

**Finding 3 (recommendation: evaluator training).** Of the 6 outputs Finding 2 confirms added unsupported claims, the human evaluator's original single-pass reference assessment caught only 1 (T03); the other 5 (T01, T06, T07, T08, T09) were missed entirely until the LLM-as-a-judge flagged them and each was independently reread against its source prompt. This is better explained as the human evaluator's single-pass assessment under-catching real issues than as the LLM-as-a-judge over-triggering: a real, disclosed instance of the brief's own "is the LLM judge creating the apparent pattern" check, resolved the opposite way it's usually framed. A system change isn't the right response to this specific finding: the underlying defect already has its own generation-side recommendation in Finding 2, and this finding is about the review process missing it, a separate, evaluation-side gap regardless of how Finding 2 plays out. Retrain the human evaluator to catch explicit "don't add X" instructions instead, since that's the specific miss here.

*In a real evaluation system, a divergence like this is a training signal about the human evaluator, not a reason to trust the judge less. This project does not action any of the following; it only names them as the kind of options a real system would weigh:*

- *Fold the specific pattern this finding surfaced (missed violations of explicit negative constraints) into evaluator training or annotation guidelines, since it's a repeatable, nameable gap rather than general inattention.*
- *Track human-vs-judge agreement per dimension over time (e.g. Cohen's kappa) so a calibration gap like this one surfaces from ongoing data rather than a one-off ten-task review: this run's evidence is that the two assessors matched exactly on `linguistic_conventions`/`spelling` (Finding 1) while diverging sharply on `accuracy`/`addition`, so the gap is dimension-specific, not a blanket reliability problem with either assessor.*
- *When a judge flag carries a specific, checkable rationale (naming exactly which claim isn't supported and why), route it to a second human look before the reference assessment is treated as final, rather than either accepting or dismissing it unreviewed.*
- *Some disagreement won't resolve cleanly even after recalibration (T05's catch here is genuinely borderline), so a real system still needs a lightweight adjudication step for cases neither recalibration nor training will settle.*

See the "Project status" note in [README.md](../README.md) for current phase.

## Scoring-threshold selection

The point values and status bands were chosen before seeing the V1 results, as a simple, legible policy: one minor issue alone should not fail an otherwise-good output; a handful of minor issues, or a single major issue, should trigger revision rather than an automatic pass; and any critical issue, or five-plus points of any kind, should fail regardless of how the rest of the copy reads. They are stored in `data/rubric.json` specifically so they can be inspected and challenged rather than taken on faith.
